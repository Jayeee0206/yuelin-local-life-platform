# 可靠秒杀失败矩阵

本文记录秒杀订单链路的设计不变量、故障窗口、预期恢复动作与证据边界。它是长期质量规范，不是某次测试报告。

## 1. 核心不变量

1. 同一用户对同一优惠券最多存在一个有效订单，数据库唯一约束是最终防线。
2. Redis 预扣必须原子地校验库存和购买资格。
3. 重复消息不得重复创建订单或重复扣减数据库库存。
4. 发布失败、不可路由或恢复次数耗尽时，补偿必须幂等归还 Redis 库存和购买资格。
5. 数据库事务未成功提交时，消费异常不得被吞掉。
6. 已落库订单不得被超时任务误补偿。
7. Redis 与数据库差异必须可审计，自动修复策略应保守且可追踪。

## 2. 故障矩阵

| 故障点 | 可能状态 | 预期行为 | 代码级证据 | 仍需真实环境验证 |
|---|---|---|---|---|
| Lua 校验拒绝 | 未预扣 | 返回库存不足或重复下单，不发消息 | Lua 返回码与服务分支测试 | Redis 版本兼容及高并发原子性 |
| Redis 预扣后，发送调用同步抛错 | 有预约、无可靠消息 | 幂等补偿并向调用方报告失败 | 发布异常与补偿分支测试 | 网络断连时客户端真实异常类型 |
| Broker Publisher Nack | 有预约、消息未确认 | Confirm 回调触发幂等补偿 | Nack 回调测试 | Broker 真实 Nack 和回调时序 |
| Mandatory Return | 有预约、消息不可路由 | 从原消息识别订单并幂等补偿；畸形消息只记录告警 | Return 正常/畸形分支测试 | Exchange、routing key 和 Return 的真实组合 |
| Publisher Ack 后应用崩溃 | 有预约、消息可能已入 Broker | 消费者正常处理；超时对账在必要时用原订单号重投 | Ack 与对账分支测试 | 崩溃窗口、Broker 持久化和重启恢复 |
| 同一消息重复投递 | 订单可能已存在 | 先检查订单；不得重复扣库存 | 消费者幂等测试 | Redelivery 标记与并发消费者时序 |
| 两个消费者并发插入 | 唯一索引竞争 | 一个提交；另一个事务回滚并按重复消息收敛 | `DuplicateKeyException` 分支测试 | MySQL 并发连接下的锁与回滚 |
| 数据库临时故障 | Redis 已预扣、订单未提交 | 异常传播给监听容器并进入有限重试 | 异常传播测试及监听重试配置 | Broker 重投、退避和死信行为 |
| 数据库提交成功，清理预约前崩溃 | 订单存在、预约仍在 | 对账发现数据库订单后只清理预约，不补偿库存 | 已有订单对账分支测试 | 重启后扫描范围和最终收敛时间 |
| 预约超时且未达恢复上限 | 订单不存在、预约存在 | 使用原订单号重投，避免制造第二业务身份 | 对账重投测试 | 调度并发、重复扫描和真实消息链路 |
| 预约超时且达到恢复上限 | 订单不存在、预约存在 | 停止重投并执行幂等补偿 | 恢复上限测试 | 大量积压下的吞吐与告警 |
| Redis 或数据库不可读 | 对账信息不完整 | 不做破坏性猜测；记录失败并等待下轮 | 异常分支测试应保持保守行为 | 长时间故障、恢复后补扫和监控 |
| Redis 与数据库库存漂移 | 状态不满足审计约束 | 生成结构化差异，交由告警/处置流程 | 库存审计测试 | 故障注入后的差异分类和人工流程 |

“代码级证据”表示仓库存在对应隔离测试；只有在目标提交上实际执行并通过后，才可作为该提交的验证结果。

## 3. 建议执行顺序

### 3.1 不启动基础设施

```bash
mvn -B test
```

重点复核发布确认、消费者幂等、数据库异常传播、超时重投、恢复上限与库存审计相关测试。

### 3.2 隔离集成环境

在可丢弃的 CI 环境启动 MySQL、Redis 和 RabbitMQ，验证：

1. 数据库唯一索引及真实事务回滚；
2. Lua 脚本在目标 Redis 版本上的行为；
3. Publisher Confirm、Mandatory Return、重投和死信；
4. 消费成功后的预约清理；
5. 中间件短暂不可用后的恢复。

### 3.3 生产近似环境

使用无真实用户数据的专用环境执行：

1. Redis 预扣后强制终止应用，再重启并观察预约恢复；
2. 在消息已确认、数据库提交前后分别注入故障；
3. 暂停消费者制造积压，再恢复并验证幂等；
4. 让数据库或 Redis 短时不可用，确认不会错误超卖或破坏性补偿；
5. 在目标并发下记录吞吐、分位延迟、错误率、积压与最终收敛时间；
6. 验证监控、告警、人工处置和回滚手册。

## 4. 证据边界

以下结论不能仅由单元测试、静态检查或一次 CI 成功推出：

- 生产环境不会超卖；
- 任意崩溃窗口都能在固定时间内收敛；
- Broker、数据库和 Redis 的目标配置与测试环境完全一致；
- 已达到业务容量或可用性目标；
- 告警、备份和人工响应流程有效。

每次发布应在外部受控系统记录提交号、环境、故障注入步骤、观察指标、通过项和未执行项。证据中不得包含真实凭据、Cookie、个人信息、本机绝对路径或未脱敏日志。
