# 故障恢复操作边界

## MQ 故障

- 普通重复投递同一个 orderId：如果数据库已存在同身份订单，执行 Redis complete；不能使用“另一个订单重复预约”的退库存路径。
- Return/Nack/发送异常/超时上限：先在数据库锁定 orderId。已有订单则 complete；否则持久记录 CANCELLED 后再补偿 Redis。消费者使用同一行锁，CANCELLED 迟到消息不能落单。
- 数据库不可用时不能猜测订单失败并补库存；保留 Redis pending，恢复后重新核对。补偿落库后 Redis 操作失败可重试，取消围栏不会丢失。
- 消费者的数据库失败经有限重试后进入 DLQ；pending 仍可被调度器重发。毒消息只进入 DLQ，不能自动清空或无限重播。
- DLQ 人工操作：保存原 payload、x-death、异常及关联订单；确认身份和业务状态；修复根因后有界重发有效消息，记录操作者和结果。无效 payload 隔离归档；禁止直接删除整个生产 DLQ。
- 定期核对 MySQL 可售库存、Redis 可售库存、pending、订单唯一性、取消围栏、主队列及 DLQ。活动进行中有 DB commit→Redis complete 短窗口，单次审计告警不应触发覆盖库存；停写并静默队列后再做最终对账。

Redis 与 MySQL 不构成跨存储事务；围栏防止“已取消仍落单”和“已落单却补库存”，不宣称具有跨存储原子提交。Redis 持久化损失、灾难恢复与多机可用性仍需部署级方案。

## 备份恢复

保存一致性快照，校验 SHA256、行数和关键业务约束，在独立数据库/图片卷先还原再切换。CI 会对测试审计表执行真实 mysqldump→删除测试行→恢复→逐行校验；这是恢复机制样例，不是生产全库恢复演练证据。生产全库 RPO/RTO、密钥备份、时间点恢复必须另外验收。

## 发布前置条件

真实验证码通道、HTTPS、强凭据、服务隔离、管理员 ID 清单、备份监控、告警、磁盘配额、库连接与锁等待、RabbitMQ/Redis 持久化及支持中的框架版本必须由部署负责人确认。当前 Spring Boot 2.7 / Vue 2 的生命周期风险仍是生产发布阻断项。
